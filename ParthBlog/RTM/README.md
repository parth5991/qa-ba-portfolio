## RTM Structure

The matrix uses the following five columns:

1. **ReqID:** Unique identifier assigned to each functional requirement.
2. **Feature:** Name of the module or functional area.
3. **Summary:** Brief description of the expected functionality.
4. **TCs:** Total number of documented test cases covering the requirement.
5. **Status:** Indicates the requirement's test coverage status.

## Coverage Status

The following coverage statuses are used:

- **Covered:** The documented test cases provide coverage for the requirement.
- **Partially Covered:** Some aspects of the requirement have documented test coverage, but additional coverage may be needed.
- **Not Covered:** No corresponding test coverage has been documented.

All 11 ParthBlog requirements are currently marked as Covered.

## Traceability Approach

The RTM maintains requirement-level traceability by recording the total number of test cases associated with each functional requirement.

Individual test case IDs and detailed test scenarios are maintained separately in the ParthBlog manual test-case workbook.

The RTM is intentionally kept concise and does not duplicate individual test case information.

## Execution Status

The RTM represents documented test coverage and does not indicate actual test execution results.

ParthBlog is a fictional portfolio project, and a working application is not currently available for execution.

All test cases remain in `Not Started` status, and no Pass/Fail results or execution metrics have been claimed.
